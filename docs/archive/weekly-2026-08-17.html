Stealing Reasoning Traces from Proprietary LLM APIs

洞察如果结论成立，厂商用隐藏思维链构建的护城河比想象中脆弱得多——被窃取的推理轨迹恰恰是蒸馏小模型最值钱的燃料，这会直接改变闭源与开源之间的能力扩散速度。更值得注意的是漏洞性质：它不是模型问题，而是 API 与状态管理的系统设计问题，说明前沿实验室在「模型能力」与「模型周边工程安全」上的投入并不对称。今日 arXiv 上还有 Convergent Detour Hijacking（针对 skill-based LLM agent 的资源放大攻击）等多篇同类工作，agent 与推理服务的攻击面正在被系统性挖掘。

BDH-CQ：结合循环隐空间推理的上下文学习

BDH-CQ: In-Context Learning with Recurrent Latent Reasoning

论文提出 BDH-CQ，一种把上下文学习与循环隐空间推理结合的推理模型：推理时输入持续更新模型的循环记忆，随后模型在高维隐空间中通过迭代计算求解问题，不需要把中间推理过程用语言显式写出。作者在公开的 ARC-AGI-1 评测集上做了评估，并用可控的类 ARC 干预实验分析模型从示例中学到了什么、能否稳定应用推断出的变换规则。一个仅 150M 参数的配置达到 29.5% 的 pass@2，单任务推理成本折算约 0.0007 美元。

洞察这条信号的杀伤力不在绝对分数，而在三个数字的组合：150M 参数、29.5% pass@2、0.0007 美元。过去两年行业的默认路径是「参数放大 + 显式思维链 + 测试时多采样」，代价是推理成本随难度线性甚至超线性上升。BDH-CQ 走的是相反方向——把推理搬进隐空间循环，让计算深度而非 token 长度承担推理负担。它与今日另一条 U-OPSD（无外部监督的 on-policy 自蒸馏，182 upvotes）以及 AI4AI harness 式强到弱能力迁移形成同一趋势带：后训练与推理阶段的效率革新，正在从「买更多算力」转向「改变计算结构」。如果这条路线继续验证，未来 12 个月最稀缺的不是会调超大模型的人，而是同时懂循环架构、隐空间表示与测试时计算调度的复合型研究者。
招聘行动把「latent reasoning / recurrent depth / test-time compute 架构」立为独立的 mapping 赛道，不要再混进泛 reasoning 池。优先锁定 BDH-CQ、U-OPSD 这类论文的一作与通讯作者，以及 ARC-AGI 榜单上小模型高分方案背后的团队——这批人往往来自学术实验室或小团队，尚未被大厂标准化 offer 覆盖，是性价比最高的窗口期。面谈时用「如何在不增加输出 token 的前提下提升推理深度」作为筛人问题，能快速区分真正做过架构的人和只做 prompt 与数据的人。

不同模型的 token 不是同一种计价单位

On tokens and prices per token. I said I’d write more about this, so here goes: an OpenAI token != another model’s toke

OpenAI 的 Thibault Sottiaux 指出，各家模型对同一段文本切分出的 token 数不同，单价低不代表总账单低；他举例 GPT-5.6 Sol 处理同样文本用 766 个 token，而 Claude Opus 5 约需 1170 个，相差约 34.5%，真正该看的是每个成功结果的成本。

英文原文 EN

On tokens and prices per token. I said I’d write more about this, so here goes: an OpenAI token != another model’s token. We compare AI prices in dollars per million tokens as if a token were a standardized unit, like a gram or a kilowatt-hour. It isn’t. Different models use and produce the exact same text using different numbers of tokens, which means a lower price per token does not necessarily mean a lower bill. Imagine two identical pizzas. One is cut into 8 slices at $2 each. The other is cut into 16 slices at $1.25 each. The second place advertises cheaper slices, but the whole pizza costs $20 instead of $16. Bummer ... your stomach doesn't actually care about the number of slices you just ate. I know you are hungry now, but back to tokens. In one small comparison spanning English, technical, multilingual, and numerical text, the tokenizer we use for GPT-5.6 Sol used 766 tokens versus an estimated 1,170 for Claude Opus 5. That's a very significant difference of about 34.5% fewer tokens. You can get the same exact text, but pay for all those extra tokens. The price per token doesn't really tell this story. Even correcting for tokenizer differences misses the bigger point. What actually matters is price per successful outcome, and for that you can use benchmarks as a starting point, but really you have to try it and measure on your own use cases. That's all. May the tokens flow.

英文原文 EN

A weird experiment I've been trying the last few weeks is having Claude take over day-to-day maintenance of our apps. Seeing early signs of life that this might be possible. The setup is straightforward: we have a Slack channel called proj-claude-maintains-apps. In it, Claude Tag runs a bunch of daily routines across iOS, Android, Desktop, web, CLI, and Agent SDK: - Crash fuzzer: open the app in a simulator and tap around to find ways to crash it, then root cause and fix the crashes - Dup unifier: scans the codebase for similar-yet-slightly-divergent abstractions, and puts up PRs to unify them - Dead-code remover: removes statically unreachable code, and adds logging to suspected dead code to check if it's really dead and if so, remove it the next day - Abstraction police: fixes leaky abstractions - a bunch more..
